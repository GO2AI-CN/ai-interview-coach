# 为什么你的 Agent 总忘事？记忆系统入门第一课

你做的 AI 面试教练昨晚陪用户练了一小时，摸清了他「goroutine 泄漏题一被追问就卡壳」。今天用户再次打开，教练却像第一次见面：「你好，我们先从自我介绍开始。」——昨晚那场面试，白练了。

这不是模型的锅，是架构里根本没有「记忆」这一层。所有信息都活在这一轮请求的上下文窗口里，请求结束，全部蒸发。这个系列我们用 Go 从零搭一套完整的 Agent 记忆系统：摘要压缩、事实抽取、衰减召回、遗忘 GC，最后装回面试教练，让它第二次见面就直戳薄弱点。配套代码在开源仓库 [ai-interview-coach](https://github.com/GO2AI-CN/ai-interview-coach) 的 `memory/` 目录，技术栈仍然只有 openai-go v3.89.0 + 标准库。

## 一、上下文窗口为什么不是记忆

「现在窗口都 100 万 token 了，把历史全塞进去不就行了？」这是最常见的误解，四个理由都站不住：

**贵**。每次请求都按全量 token 计费。一场面试原始记录两万字，第十次会话时你要为前十场的全部记录反复付费，账单线性变二次方。

**乱**。原始记录里寒暄、废话、错误尝试和关键事实搅在一起。塞得越多，模型越难分辨哪句重要——这不是容量问题，是信噪比问题。

**短**。窗口的生命周期就是一次会话。用户关掉页面，上下文没了，下次还是从零开始。跨会话的连续性恰恰是最值钱的产品体验。

**没法算**。堆在窗口里的历史是一坨文本，你不能按类型筛选、按重要性排序、按时间衰减——而这些正是记忆系统要干的事。

结论：上下文窗口是「工作台」，记忆系统是「档案柜」。工作台用完要清空，档案柜才负责长期保存。

## 二、一张表划清：记忆、RAG、缓存、黑板

读到这里，看过本号前面几个系列的读者会犯嘀咕：RAG 不也是存东西再检索？语义缓存不也是存问答？黑板不也是共享读写？它们和记忆的边界在哪？这张表一次讲清，值得收藏：

| 机制 | 存的是什么 | 谁写谁读 | 解决什么 | 本号出处 |
|---|---|---|---|---|
| 记忆系统 | Agent 自身的经历：发生过什么、学到什么 | Agent 写，未来的自己读 | 跨会话连续性、个性化 | 本系列 |
| RAG | 外部知识：文档、FAQ、代码库 | 人提前灌入，Agent 只读 | 模型不懂的领域知识 | RAG 系列 8 篇 |
| 语义缓存 | 问题→答案的只读副本 | 系统自动写，命中即返回 | 省钱、降延迟 | 工程化系列第 5 篇 |
| 共享黑板 | 一次任务中的中间产出 | 多 Agent 互写互读，任务结束即弃 | 多 Agent 协作的工作内存 | 多智能体系列第 4 篇 |

一句话区分：**RAG 是「读别人的书」，记忆是「记自己的账」**；缓存只进不出永不变，记忆会更新、会衰减、会被遗忘；黑板随任务生灭，记忆随用户长生。边界划清，后面的设计才不会张冠李戴。

## 三、四类记忆：不同寿命，不同待遇

认知科学把人的记忆分成几类，这套分类搬到 Agent 上意外地好用。同样是收藏向的一张表：

| 类型 | 存什么 | 寿命 | 面试教练里的例子 | 本系列对应篇 |
|---|---|---|---|---|
| 短期记忆 | 本次会话的工作上下文 | 一场会话 | 刚才第 2 题答了什么 | 第 2 篇 |
| 情景记忆 | 发生过的具体事件 | 长期，会衰减 | goroutine 泄漏题追问时沉默 | 第 3、4 篇 |
| 语义记忆 | 从事件提炼出的事实 | 长期 | 目标岗位 Go 后端、3 年经验 | 第 3、5 篇 |
| 程序记忆 | 怎么做事的规则偏好 | 长期，最稳定 | 卡壳时先给提示再给答案 | 第 5 篇 |

分类不是学术洁癖，是为了回答两个工程问题：**这条记忆该活多久？召回时该排多靠前？** 短期记忆会话结束就清，程序记忆几乎不动，情景记忆按时间衰减——寿命不同，存储和检索策略自然不同。不分类的记忆系统，最后都会退化成「一个越堆越满的杂物间」。

## 四、动手：一组接口 + 最小实现

整个系列的地基是两个类型和一个接口。先看记忆单元和四类枚举，`memory/memory.go`：

```go
// Entry 是一条记忆的最小单元。
type Entry struct {
	ID         string    // 唯一标识，写入时生成
	Kind       Kind      // 记忆类型，决定生命周期与检索策略
	Content    string    // 记忆正文，必须是一句完整的话，存碎片等于没存
	Importance float64   // 重要性 0~1，写入时打分，检索时加权
	Source     string    // 来源：哪次会话、哪个 Agent 写下的，便于回溯
	CreatedAt  time.Time // 写入时间，第 4 篇时间衰减要用
}
```

每个字段都是伏笔：`Kind` 对应上面的四类表，`Importance` 和 `CreatedAt` 是第 4 篇召回打分的输入。再看存储契约：

```go
// Store 是记忆系统的最小接口：写入、按条件召回、删除。
type Store interface {
	Save(ctx context.Context, e Entry) error
	Recall(ctx context.Context, q Query) ([]Entry, error)
	Forget(ctx context.Context, id string) error
}

// Query 描述一次召回的条件。
type Query struct {
	Kinds []Kind // 限定记忆类型；空表示不限
	Text  string // 检索词；本篇先精确包含匹配，语义检索留给第 4 篇
	Limit int    // 最多返回几条，0 表示不限
}
```

接口只有三个方法，和仓库里多智能体系列的 `Agent` 接口一个思路：契约先行，实现可换。本篇用 `InMemoryStore`（一个 map 加读写锁）把读写流程跑通，向量库实现留给后续篇章。

demo 模拟面试教练的两场会话：第一场结束后，不把两千字原始记录全塞进第二场，而是沉淀出 3 条记忆；第二场开场只召回「情景+语义」两类，拼成出题策略：

```go
// 第二场面试开场：召回情景+语义记忆，拼进系统提示词
got, err := store.Recall(ctx, memory.Query{
	Kinds: []memory.Kind{memory.KindEpisodic, memory.KindSemantic},
	Limit: 5,
})
if err != nil {
	log.Fatal(err)
}
fmt.Println("第二场开场，教练记得：")
for _, e := range got {
	fmt.Printf("  [%s|重要性%.1f] %s\n", e.Kind, e.Importance, e.Content)
}
```

`go run ./cmd/memory-demo` 的输出：

```text
原始记录 1891 字 → 沉淀为 3 条记忆

第二场开场，教练记得：
  [semantic|重要性0.7] 目标岗位是 Go 后端，自称 3 年经验
  [episodic|重要性0.9] goroutine 泄漏题：能说出 channel 未关闭，但追问具体场景时沉默
→ 本场出题策略：goroutine 泄漏加追问，按后端 3 年经验定难度
```

1891 字记录压成 3 条记忆，第二场开场的上下文从「一坨文本」变成「3 行结构化要点」——这就是档案柜和工作台的区别。demo 不接大模型也能跑：记忆框架的正确性不该依赖模型的稳定性，骨架先跑通，第 3 篇再把「人工沉淀」换成「LLM 自动抽取」。

## 五、写入时的三条例行规矩

第一篇文章最后留一份清单，是后面七篇反复引用的纪律：

- **正文必须是一句完整的话**。「goroutine 泄漏题」是碎片，「goroutine 泄漏题追问时沉默」才是记忆。三个月后召回出来的碎片，连你自己都读不懂。
- **写入时就打重要性分**。事后补打分要重扫全库，成本极高；打分标准可以提前定死：答错的题 0.9，背景信息 0.7，偏好 0.6。
- **永远带上 Source**。记忆会错、会过时，没有来源的记忆无法回溯、无法证伪，出问题时只能全库清空。
