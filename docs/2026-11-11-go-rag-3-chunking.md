# RAG 切分实战：chunk 怎么切，检索才不翻车

> 系列三「RAG 与向量检索」第 3 篇。上一篇我们接上了真 embedding（bge-m3，1024 维），但先别高兴——如果你把整篇一万字的文章直接丢进嵌入接口，得到的向量是"一锅粥"的平均语义。本篇解决 RAG 里**最影响效果却最少被讲透**的工程环节：文档切分（chunking）。

测试素材就是本仓库已开源的 16 篇教程（github.com/GO2AI-CN/ai-interview-coach），三种切法跑同一组问题，用实测数据说话。

## 一、整篇嵌入错在哪

把一篇 5000 字的文章变成一个向量，有三个硬伤：

1. **语义稀释**：文章既讲追问策略又讲部署，向量只能表示"这篇文章大概关于面试教练"，问具体问题时它和所有文章的距离都差不多，排不出先后；
2. **输入上限**：embedding 模型输入上限 8192 token，长文档直接装不下；
3. **无法溯源**：就算检索"命中"了整篇文章，LLM 拿到的上下文是整个 5000 字，成本高，而且读者问"出处是哪一节"时你答不上来。

切分的目标：让每个 chunk **语义自包含**——只看这一块，就能独立回答某类问题。这也是第 5 篇"引用溯源"的前提。

## 二、三种切法，和中文世界的两个坑

三种主流策略，实现都简单，差别在语义完整度和元数据：

- **固定窗口**：每 N 字一块、块间重叠 M 字。实现最简，但块从句子中间断开，开头就是半个句号；
- **段落合并**：按空行分段，贪心合并到上限。块内永远是完整段落，阅读体验好；
- **标题小节**：按 Markdown `##` 标题切，一节一块。块自带"出处"属性，天然适合溯源。

中文场景有两个专属坑，踩过的都懂：

1. **按字节切 = 乱码**：Go 的 `len(string)` 数的是 byte，一个汉字 3 字节，按 byte 下刀会把汉字切成 invalid UTF-8 的碎片。必须转成 `[]rune` 再切；
2. **表格和代码块会被拦腰斩断**：固定窗口切到 Markdown 表格中间，出来的 chunk 是一堆残缺的 `|---------|`，语义全毁。缓解办法：代码块整体视为不可切分单元，或优先用标题/段落边界。

## 三、代码：三种策略，核心各十几行

仓库新增 `rag/chunk/chunk.go`。chunk 是检索和溯源的最小单元，元数据从切分时就带好：

```go
// Chunk 是切分后的最小检索单元。
type Chunk struct {
	Text string `json:"text"` // 正文内容
	File string `json:"file"` // 来源文件名，如 2026-11-06-go-rag-1-intro.md
	Head string `json:"head"` // 所属 Markdown 标题路径，如 "四、追问策略"
	Seq  int    `json:"seq"`  // 在文件内的序号，用于排序和去重
}
```

固定窗口策略的核心循环，注意 `[]rune` 转换这一行，它就是防乱码的关键：

```go
runes := []rune(text) // 按字符切，不按 byte：byte 切中文会出乱码
stride := size - overlap
for start := 0; start < len(runes); start += stride {
	end := min(start+size, len(runes))
	out = append(out, Chunk{Text: string(runes[start:end])})
	if end == len(runes) {
		break
	}
}
```

标题策略的主循环——遇到 `## ` 就收尾旧块、开新块，标题路径记进 `Head`：

```go
for _, ln := range lines {
	if strings.HasPrefix(ln, "## ") { // 遇到新标题：先收尾旧小节
		flush()
		head = strings.TrimSpace(strings.TrimPrefix(ln, "## "))
		continue
	}
	if strings.HasPrefix(ln, "# ") { // 文章大标题只进 head，不进正文
		head = strings.TrimSpace(strings.TrimPrefix(ln, "# "))
		continue
	}
	body.WriteString(ln) // 小节正文累积，超长再内部按窗口切
	body.WriteString("\n")
}
flush()
```

## 四、实测：16 篇文章，同一问题，三种切法

`go run ./rag/cmd/chunkdemo` 对两个测试问题分别检索，完整实测结果：

| 切分策略 | 块数 | 平均字数 | 问题1 Top1（判断追问） | 问题2 Top1（HTTP 对外服务） |
| --- | --- | --- | --- | --- |
| 固定窗口 300/50 | 154 | 290 | 正确文件，块从半个句号开始 | mcp-1 的 JSON-RPC 示例段 |
| 段落合并 300 | 209 | 313 | 出题段落（擦边） | mcp-2 的 stdio 段落 |
| 标题小节 | 160 | 240 | **精确命中「追问策略」整节** | mcp-1「MCP 是什么」节 |

三个结论：

1. **标题小节节节胜利**：问题 1 直接命中"三、追问：判断回答深浅的两把尺子"整个小节，边界干净、自带出处；固定窗口的 Top1 是一块以"。"开头的碎片，拿这种上下文喂给 LLM，答案质量可想而知。
2. **分数差距比想象中温和**（0.645 vs 0.664），但上下文质量天差地别——检索排序看分数，生成效果看块的质量，两者不是一回事。
3. **别高兴太早：问题 2 三种切法全没排进正主**（第 7 篇《远程 MCP：HTTP/SSE 传输》在三个 Top-2 里都缺席）。这是下一阶段的活——top-k、混合检索、重排序，第 6 篇专门"问诊"。

顺带一个反直觉数据：段落合并产生了 209 块，比固定窗口还多——因为重叠段落被复制了一份。重叠不是免费的，它以存储和嵌入成本换取边界上下文。

## 五、chunk 元数据设计清单

切分时就该想好的事，事后补很贵。收藏这份清单：

- [ ] `File`：来源文件——溯源的底线，没有它命中了也说不清出处；
- [ ] `Head`：标题路径——回答里能直接写"出自《XX》第 N 节"；
- [ ] `Seq`：文件内序号——支持按序重组、邻块扩展（第 6 篇讲"命中块前后各扩一块"）；
- [ ] 长度上限：300~500 字是经验甜点区，太短语义不全，太长稀释严重；
- [ ] 重叠 10%~15%：缓解边界切断，代价是块数增多；
- [ ] 代码块/表格整体保护：宁可块大一点，不要切出碎片。
