# 让 AI 回答有出处：Go 流式问答全链路实战

你跟着这个系列走完了切分、嵌入、入库，敲下 `go run ./rag/cmd/ask`，看着终端里弹出的三条命中块——挺有成就感的。但先别急着高兴：能把相关段落找出来，距离「能用」还差一整条问答链路。

真实的 RAG 产品不是检索 demo。用户问一句话，系统要在几百毫秒内完成检索、拼 prompt、调大模型、流式吐出回答，并且每个结论都能回查原文出处。任何一环掉链子，体验都会从「智能问答」退化成「高级搜索框」。

这篇就把最后一环补上：我们用 Go 写一个完整的多轮问答 CLI，把前四篇的零件全部串起来——检索、prompt 组装、SSE 流式生成、引用溯源，全部实测跑通。代码已开源在仓库（见文末），跟着敲一遍，你的 RAG 就有产品样了。

## 一、完整链路长什么样：四步，每步一个坑

先建立整体图景。用户敲下一行问题，到我们看到流式输出的回答，中间经过四步：

| 步骤 | 做什么 | 最容易踩的坑 |
| --- | --- | --- |
| ① 检索 | 问题嵌入成向量，向量库 top-k | top-k 取多少全靠拍脑袋 |
| ② 拼 prompt | 命中块编号注入 + 下指令 | 模型开始自由发挥、编造出处 |
| ③ 生成 | 调 LLM API，SSE 流式接收 | 傻等全文，首 token 慢体验差 |
| ④ 溯源 | 把 [n] 映射回文件小节 | 回答了但读者无法核对原文 |

这张表值得收藏——它不是理论，是接下来每一节的实测路线图。我们自底向上把四步代码写完，再看整体跑起来的效果。

## 二、拼 prompt：给资料编号，是给模型上缰绳

第 4 篇的 ask 命令只打印命中块，这次要把它们拼进 prompt。核心设计有三个：

**资料编号注入。** 每条命中块前面加上 `[1] [2] [3]` 的编号，编号在 system 指令里声明含义——这是后面引用溯源的基础设施：

```go
// Build 把问题和命中块组装成 system + user 两条消息的内容。
func Build(question string, hits []store.Result) (system, user string) {
	var b strings.Builder
	b.WriteString("你是「Go2AI之路」知识库问答助手。请只依据下面编号的资料回答，" +
		"在相关句末用 [n] 标注出处编号；资料没有覆盖的内容直接说明\"知识库中没有相关信息\"，不要编造。\n\n资料：\n")
	for i, h := range hits {
		fmt.Fprintf(&b, "[%d] 《%s》§%s（相关度 %.2f）\n%s\n\n",
			i+1, h.Chunk.File, h.Chunk.Head, h.Score, h.Chunk.Text)
	}
	return b.String(), "问题：" + question
}
```

注意 system 指令里那句「资料没有覆盖就直接说明，不要编造」——它不是客套，是防幻觉的硬约束。实测效果下面就能看到。

**prompt 包不依赖任何 SDK。** `Build` 返回的是两个纯字符串，不是 openai-go 的消息类型。这一层今天接 DeepSeek，明天换 Kimi、换 Claude，代码零改动。依赖倒置做在包边界上，是这个小项目里我最满意的一处设计。

**消息组装：system 每轮重建，历史只存问答对。** 多轮对话时，每轮新问题会检索出新的资料块，system 必须跟着换；而历史消息里只追加干净的「问题 + 最终回答」，绝不能把上一轮的检索资料留在历史里——否则第二轮的 prompt 会塞满过期上下文，token 费用和干扰一起爆炸。

## 三、SSE 流式：首 token 即正义

问答产品的体感速度，看的是首 token 延迟，不是全文生成耗时。等全文返回再显示，用户盯着转圈 8 秒；流式输出第一个字 1 秒内出现，后面慢慢吐，体感就是「快」。

openai-go v3 的流式接口把 SSE 解析全包了，我们要写的核心循环短得惊人：

```go
stream := cli.Chat.Completions.NewStreaming(ctx, openai.ChatCompletionNewParams{
	Model:    openai.ChatModel(model), // DeepSeek/Kimi 等兼容端点同一套代码
	Messages: msgs,
})
fmt.Print("\nAI> ")
var answer strings.Builder
for stream.Next() {
	delta := stream.Current().Choices[0].Delta.Content
	answer.WriteString(delta)
	fmt.Print(delta) // 边收边打印，不等全文
}
if err := stream.Err(); err != nil { log.Printf("生成失败: %v", err); continue }
_ = stream.Close()
```

三个细节值得记住：`NewStreaming` 和普通请求共用 `ChatCompletionNewParams`，只是返回变成流；每个 chunk 的 `Choices[0].Delta.Content` 是增量文本，拼接起来才是完整回答；循环结束后一定要看 `stream.Err()`——流式请求的错误是延迟抛出的，网络中断在循环里看不出来。拼好的完整回答存进历史，供下一轮上下文使用。

## 四、实测：引得出处，也拒得干脆

代码写完立刻实跑（库内 260 块，模型走 DeepSeek 兼容端点）。先看正常发挥：

> **问**：面试教练怎么判断回答太浅、决定追问？
> **答**：……主要靠「两把尺子」：1. 自评置信度：让模型给自己的回答打 1~5 分，低于阈值说明它自己都觉得虚；<3 分 → 必追问 [1] 2. 关键点覆盖度：对照该题的 checkpoints，看用户命中了几条；覆盖率 <60% → 追问缺失点 [1] ……
> **引用来源**：[1] 《2026-10-27-ai-interview-coach-1.md》§三、追问：判断回答深浅的两把尺子（相关度 0.65）

回答末尾的 `[1]` 就是第二节埋的编号，读者可以拿它对照来源清单，直接回查原文小节。RAG 问答和聊天机器人的分水岭就在这里：**结论可验证**。

再看防编造约束的实测——我故意问了一个库里不可能有的问题：

| 实测问题 | Top1 相关度 | 系统行为 |
| --- | --- | --- |
| 面试教练怎么判断回答太浅、决定追问？ | 0.65 | 精确命中第 1 篇追问策略小节，标注 [1] |
| Python 的 GIL 是什么？ | 0.46 | 老老实实回答「知识库中没有相关信息」 |
| 追问策略用到了哪几个判断信号？（第二轮） | 0.64 | 延续上文语境，仍标注 [1] 溯源 |

GIL 那次，检索回来的三条最高也只有 0.46 相关度，模型没有找到任何支撑材料——它没有硬编一个「GIL 是 Python 的全局解释器锁……」出来，而是按指令拒答了。这张表里的三组数据值得细品：系统知道什么、不知道什么，全靠 prompt 里那句「不要编造」兜住。

## 五、多轮对话：朴素方案的命门在指代

我们的多轮方案很朴素：历史消息原样回传，每轮新问题独立嵌入、独立检索。对独立问题，它工作得很好（见上表第三轮）。但对**指代省略**会翻车，实测为证：

> **第一轮**：面试教练怎么判断回答太浅？
> **第二轮**：这个覆盖率的阈值在哪里改？

第二轮的「这个覆盖率」依赖第一轮上下文，单独嵌入后检索彻底跑偏——top-3 命中全变成了 MCP 系列的文章，相似度只有 0.50 上下，模型只能再次拒答。雪上加霜的是，第一轮因为措辞稍变（少了「决定追问」四个字），正主小节根本没进 top-3。

这是 RAG 多轮的经典痛点，工业界的主流解法是**查询改写**（query rewriting）：把带指代的问题连同历史一起丢给模型，改写成自包含的问句再检索；更进一步的 HyDE 则让模型先幻想一份理想答案，拿答案的嵌入去检索。另外 top-k 该取 3 还是 5、相似度多少以下该直接拒答，也值得用数据说话，而不是拍脑袋。

这些「检索质量进阶」正是下一篇的内容：top-k 调参、混合检索、rerank，顺手把上面翻车的案例一个个救回来。链路通了再调优，顺序不能反。
