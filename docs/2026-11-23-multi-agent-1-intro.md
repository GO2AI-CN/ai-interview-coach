# 一个 Agent 不够？多智能体协作第一课

你让一个"全能"Agent 独立完成一次技术调研：查资料、写分析、自己评审自己。前两轮还行，第三轮开始它把自己的评审意见当成了新需求，上下文里调研笔记、修改记录、自我批评搅成一团——改一处、崩三处。

这不是 prompt 写得不够好，是单 Agent 的结构性天花板到了。这一篇讲清楚为什么一个 Agent 会不够用，以及多 Agent 协作的三种基本形态。整个系列会基于 Go 从零实现一个多 Agent 协作框架，配套代码在开源仓库 [ai-interview-coach](https://github.com/GO2AI-CN/ai-interview-coach) 的 `multi/` 目录。

## 一、单 Agent 的三个天花板

把复杂度压在一个 Agent 身上，会同时撞三面墙：

**上下文爆炸**：所有角色的产出都堆进同一个对话窗口。窗口越长，模型越"健忘"，早期的约束和事实被挤到注意力边缘，开始自相矛盾。

**角色冲突**：一个系统提示词里塞了调研员、写手、评审三种人格。它们的立场天然对立——写手想赶紧交稿，评审想推翻重写。同一个上下文里两种立场互相拉扯，输出质量剧烈抖动。

**单点失败**：一个 Agent 崩了（超时、输出格式错、陷入重复），整个任务就没有退路，没有第二个角色能接手。

三面墙本质上是一件事：**一个进程承担了本该由多个角色分担的复杂度**。而解法也和软件架构一样——拆分职责、定义接口、编排协作。

有经验的读者会指出：加长上下文窗口不就行了？实测并非如此。窗口再大，"角色立场互相拉扯"的问题依然存在——评审意见混在需求描述里，模型自己分不清哪句是目标、哪句是批评。这不是容量问题，是**关注点分离**问题，和当年把单体应用拆成微服务是同一类决策。

## 二、多 Agent 的三种基本拓扑

协作方式没有标准答案，但业界实践收敛成了三种基本拓扑。这张表值得收藏，选型时对照：

| 拓扑 | 谁指挥 | 消息怎么流动 | 适合什么任务 | 风险点 | 本系列对应篇 |
|---|---|---|---|---|---|
| 主从（Orchestrator-Worker） | 中央编排者拆任务、派活、收结果 | 编排者↔工人，点对点 | 任务可拆解、步骤有依赖 | 编排者成为瓶颈和单点 | 第 2 篇 |
| 流水线（Pipeline） | 无，固定顺序一棒接一棒 | 上一棒的输出是下一棒的输入 | 阶段清晰、单向流转 | 错误会沿流水线放大 | 第 1 篇 demo |
| 黑板（Blackboard） | 无中央指挥，共享工作区协调 | 所有 Agent 读写同一块黑板 | 开放性问题、多路探索 | 写冲突、黑板越写越乱 | 第 4 篇 |

真实系统往往是三者混搭：编排者按黑板上的全局状态决定下一棒派给谁。但先把每种拓扑单独吃透，混搭才有底气。

选型的第一性问题不是"哪种先进"，而是"任务有没有清晰的产出边界"。产出物能一句话说清的任务（"出一份提纲""写一段实现"），随便哪种拓扑都装得下；产出物本身是探索性的任务（"找出这个项目最大的技术风险"），才需要黑板的自由度。

## 三、先把 Agent 抽象成接口

不管哪种拓扑，第一步都一样：给"Agent"下一个最小定义。我们在 `multi/types.go` 里用三个类型定完：

```go
// Task 是一次协作的最小单元：目标 + 输入材料
type Task struct {
	Goal   string            // 要完成什么，一句话说清
	Inputs map[string]string // 输入材料，如前文摘要、检索结果
}

// Result 是 Agent 干完活之后的交付物
type Result struct {
	Output  string // 完整产出：一段分析、一份报告
	Summary string // 一句话摘要，给编排者汇总或交给下一棒
}
```

Agent 本身只有一个名字和一个方法：

```go
// Agent 是"能干活的角色"的最小接口。
// 实现可以是大模型调用、规则引擎，甚至一个纯函数。
type Agent interface {
	Name() string
	Run(ctx context.Context, t Task) (Result, error)
}
```

刻意保持这个接口极小：**实现可以是大模型调用、规则引擎，甚至一个纯函数**。接口不绑定任何 SDK，后面五种拓扑全部建立在它上面，这是整个系列的承重墙。`Summary` 字段是专门为协作设计的——单 Agent 用不着它，多 Agent 靠它传递"这一棒干了什么"。

## 四、最小可跑 demo：一条两棒流水线

接口定了，立刻验证它能不能跑。`cmd/multi-demo` 用两个 mock agent 组成最简流水线，不接大模型也能运行：

```go
// scoutAgent 模拟"调研员"：把目标拆成调研提纲
func (scoutAgent) Run(_ context.Context, t multi.Task) (multi.Result, error) {
	outline := fmt.Sprintf("提纲：%s 的定义 → 主流方案对比 → 选型建议", t.Goal)
	return multi.Result{Output: outline, Summary: "调研提纲已就绪"}, nil
}

func main() {
	ctx := context.Background()
	// 流水线拓扑：上一棒的 Output 作为下一棒的输入
	r1, _ := scout.Run(ctx, multi.Task{Goal: "Go 项目 ORM 选型"})
	r2, _ := writer.Run(ctx, multi.Task{
		Goal:   "Go 项目 ORM 选型",
		Inputs: map[string]string{"outline": r1.Output},
	})
	fmt.Println(r2.Output)
}
```

`go run ./cmd/multi-demo` 的输出是一篇带提纲和结论的"调研初稿"。mock 的意义在于：**协作框架的正确性不应该依赖大模型的稳定性来验证**。先把骨架跑通，再把 mock 换成真模型，这也是本系列每篇的演示方式。

注意这个 demo 里藏着流水线拓扑的第一个教训：上游 `Summary` 和 `Output` 分工明确——`Output` 给下一棒当输入，`Summary` 留给日志和将来排障用。如果两棒之间只传一坨没有结构的文本，第三步加编排者时会立刻失控。

## 五、什么时候别上多 Agent

多 Agent 不是银弹，上来就拆十个角色是最常见的过度设计。这几条"别拆"清单同样值得收藏：

- **任务一轮对话能完成**：加协作纯增延迟和成本。
- **步骤间没有明确的产出物边界**：拆出来的 Agent 会互相等、互相猜。
- **总调用预算敏感**：每多一个 Agent，token 成本和失败面都翻一倍。

判断标准很简单：拆完之后，每个 Agent 的系统提示词是不是更纯粹了？如果拆完每个角色还是得"顺便干别的活"，说明拆错了，回去改任务定义。好拆的系统，每个角色的提示词都应该能用一句话向新人讲明白。
