# Agent 干得好不好？给协作链路装上轨迹评测

前五篇我们把多 Agent 系统越搭越复杂：编排者派活、Worker 之间交接、共享黑板、事件通知。系统能跑通了，但一个新的问题浮出水面——**输出结果不对的时候，你怎么办？**

三个 Agent 各写一段，最终结论看着挺像那么回事，但里面混了一句错误数据。是调研编错了？还是压测看串了行？没有记录，你只能把整条链路重跑一遍、逐段打印，靠人肉二分定位。本文给协作链路装上「行车记录仪」和「质检规则」，让问题可回放、可归因。

## 多 Agent 系统的归因困境

单 Agent 出问题是显性的：一次调用、一个输出，错了就是它错了。多 Agent 的麻烦在于**错误会沿着链路放大**：

1. 源头可能埋在第二棒——压测员把 QPS 单位看错了；
2. 传递时被放大——顾问基于错误数据「合理」地推出了错误结论，读起来毫无破绽；
3. 事后无现场——没记轨迹的话，你看到的是一团耦合的历史消息，根本没法拆开看每一棒当时拿到了什么、输出了什么。

所以轨迹（Trace）不是可选的优化项，是多 Agent 系统的必备基础设施。就像行车记录仪，平时想不起它，出了事才知道没它不行。

## 轨迹：每一棒留一段 Span

轨迹的核心数据结构很简单——每棒干完活，留一段 Span。字段要克制，因为轨迹要进日志、进评测提示词，越精炼越容易被下游用上：

| 字段 | 记什么 | 为什么必须记 |
| --- | --- | --- |
| Role | 哪个角色干的 | 归因的锚点 |
| Goal | 这一棒的任务目标 | 判断是否答非所问 |
| Input | 拿到的输入摘要 | 区分"喂错了"还是"做砸了" |
| Output | 产出摘要 | 评测质量的主要素材 |
| Latency | 耗时 | 性能抖动和慢调用的证据 |
| Err | 失败原因 | 硬伤的直接记录 |

有一点要刻意强调：**Input 只记摘要，不记全量。** 完整输入可能有几千字，全量进轨迹，存储和评测成本都吃不消。轨迹回答的问题是「当时喂了什么」，摘要（比如各输入键值对拼一行）足够支撑归因。

记录器本身零侵入：编排者不挂记录器就一行不记，挂了才在派发循环里多一段记录：

```go
start := time.Now()
r, err := w.Run(ctx, s.Task)
if o.rec != nil { // 挂了记录器才记轨迹，行为零侵入
	o.rec.Record(Span{
		Role:    s.Role,
		Goal:    s.Task.Goal,
		Input:   summarizeInputs(s.Task.Inputs),
		Output:  r.Summary,
		Latency: time.Since(start),
		Err:     err,
	})
}
```

## 评测：规则先行，模型评分留好插槽

有了轨迹，评测就是扫描轨迹的一组规则。每条规则是一个纯函数：看一眼整条轨迹，返回发现的问题清单。这个签名有个小心机——以后接入评分大模型时，模型输出也落到同一个 `EvalRule` 签名里，评测主流程一行不用改：

```go
// EvalRule 是一条评分规则：扫描整条轨迹，返回发现的问题（空=通过）。
// 规则是纯函数，可单测；以后接入评分模型时，模型输出也落到这个签名里。
type EvalRule func(Trace) []string

// Evaluate 用一组规则给轨迹打分。统一 10 分/条，简单可解释，
// 比一上来就加权平均更抗争议——先把硬伤找出来，再谈细化权重。
func Evaluate(t Trace, rules ...EvalRule) Report {
	rep := Report{Score: 100, Spans: len(t.Spans)}
	for _, rule := range rules {
		for _, p := range rule(t) {
			rep.Problems = append(rep.Problems, p)
			rep.Score -= 10
		}
	}
	if rep.Score < 0 {
		rep.Score = 0
	}
	return rep
}
```

内置三条规则覆盖最常见的硬伤，也演示了规则该怎么写：报错必扣、产出为空必扣、单棒耗时超限必报。对应到我们的系统里：`RuleAllSucceeded` 兜住执行失败，`RuleNoEmptyOutput` 兜住大模型偷懒返回空，`RuleLatencyUnder` 捕捉提示词膨胀或模型抖动。

## 实测：同一条链路，健康与划水各跑一遍

demo 把同一套编排跑两遍：第一遍三个 Worker 都正常交付；第二遍混进一个划水 Worker——调用成功，摘要却是空串。两次运行用完全相同的规则打分，输出对比：

```text
==== 健康运行 ====
得分 100，问题 0 条
==== 划水运行：benchmarker 产出为空 ====
得分 90
 - span 1 [benchmarker] 产出为空
```

注意报告里那条问题：它不仅说「产出为空」，还带上了 span 序号和角色名。这就是归因的价值——你看到 `span 1 [benchmarker]`，直接去查压测员的提示词和模型调用，而不是在三棒输出里大海捞针。

顺带一提，这个「划水」场景不是虚构的：接真实大模型时，提示词没写好、返回格式约束不严，模型极其容易返回看似成功实则空洞的结果。规则 `RuleNoEmptyOutput` 挡的就是这类「温柔的失败」——不报错，但什么都没干。

## 踩坑记录：评测系统的三个反直觉

**第一，扣分制比打分制好用。** 让规则直接打 0~100 分，不同规则的分值会互相打架；改成「100 分起扣、每条扣 10 分」，每条规则只回答一个二值问题——有没有问题。先抓硬伤，再谈加权，工程上稳得多。

**第二，规则要多小写多小，别做"综合质量分"。** 早期版本我写过一条「综合评估产出质量」的规则，里面塞了五种判断，出问题根本没法归因。拆成一条一个小问题之后，报告里的每条扣分都能对应一个具体修复动作。

**第三，轨迹要落盘成 JSON，评测才有"案发现场"。** 内存里的轨迹随进程消失，等于行车记录仪只在屏幕上回放。真实系统里把 `Trace` 序列化到文件，出问题后离线重放评测，这是可观测性的底线。本仓库 demo 聚焦评测逻辑，落盘留给接入真实大模型时一起做。

完整代码在仓库的 `multi/trace.go`（含编排器的记录器挂钩）和 `cmd/multi-trace-demo/`，`go run ./cmd/multi-trace-demo` 复现两次运行的对比输出。

## 小结与预告

至此我们解决了多 Agent 系统的质量问题：轨迹负责留证，规则负责质检，报告负责归因。零第三方依赖，评测主流程不到 20 行。

但还有个更致命的问题没解决：如果某一棒陷入死循环，或者大模型接口迟迟不返回，整条链路会卡死——评测再漂亮，系统不活着也白搭。
