## 二、top-k 调参：k=3 是甜点，再加没用

先给纯向量检索调参，实测结果：

| 方法 | hit@1 | hit@3 | hit@5 |
| --- | --- | --- | --- |
| 纯向量 | 6/10 | 9/10 | 9/10 |

两个结论。第一，**k 从 1 加到 3 是真提升**（6→9），多捞回的都是「正主在第 2、3 名」的题——榜首失手榜眼探花接住，是向量检索的日常。第二，**3 再加到 5 零收益**：k 越大，塞进 prompt 的噪音块越多、token 越贵，收益却没了。k=3 就是这个语料规模下的甜点，不是拍的，是卷子说的。

剩下的 1 道硬骨头正是开头那道翻车题：正主排第 9，调 k 救不回来。相似度挤成一团是典型的「语义稀释」——向量学的是大概意思，碰上 HTTP、SSE 这种专有名词就分不出高下。这种病要换武器治。

## 三、向量不行的地方，关键词行：手写 BM25

BM25 是搜索引擎时代的关键词排序算法，核心思想一句话：**查询词命中越多、词越稀有、文档越短，得分越高**。我手写了一版，90 行纯 Go 零依赖，go.mod 一行不动。

中文切词不装分词器：连续汉字按相邻两字切 bigram，英文数字小写化成单词，标点天然分界：

```go
case unicode.Is(unicode.Han, r): // 中日韩表意文字走 bigram
	flushLatin()
	cjk = append(cjk, r)
case unicode.IsLetter(r) || unicode.IsDigit(r): // 拉丁字母聚成单词
	flushCJK()
	latin.WriteRune(unicode.ToLower(r))
```

打分是经典公式，k1=1.5 控制词频饱和度、b=0.75 控制长度归一化，都是通行默认值：

```go
for _, t := range Tokenize(query) {
	f, ok := tf[t] // 词 t 在本文档的词频
	if !ok {
		continue
	}
	// 变体 IDF：词越稀有权重越高，且永远非负
	idf := math.Log(1 + (n-float64(x.df[t])+0.5)/(float64(x.df[t])+0.5))
	tfn := float64(f) * (k1 + 1) / (float64(f) + k1*(1-b+b*float64(x.dls[i])/x.avgdl))
	score += idf * tfn
}
```

实测 BM25 单跑成绩很差：hit@1 只有 3/10——公众号文风口语化，问题和正文关键词重合度低。但关键证据在那道翻车题上：**向量排第 9 的正主，BM25 直接排第 2**。「HTTP」「端点」这些硬词，关键词检索一抓一个准。两路各有所长，融合的动机就有了。

## 四、RRF 融合：按名次不按分数

两路结果怎么合并？加权求分是第一个坑：余弦相似度在 0~1 之间，BM25 动辄十几分，量纲完全不同，加权等于让 BM25 说了算。稳妥做法是 RRF（倒数名次融合），只看名次不看分，k=60 是原论文推荐值：

```go
// RRF 把多路排名按 1/(k+rank) 融合：名次从 1 开始，同文档分数累加
for _, ranking := range rankings {
	for i, s := range ranking {
		a := fused[id(s.Chunk)]
		a.score += 1 / (k + float64(i) + 1)
	}
}
```

三路总成绩单，这张表值得收藏：

| 方法 | hit@1 | hit@3 | hit@5 |
| --- | --- | --- | --- |
| 纯向量 | 6/10 | 9/10 | 9/10 |
| 纯 BM25 | 3/10 | 9/10 | 10/10 |
| RRF 混合 | 5/10 | **10/10** | **10/10** |

翻车题的救援明细：向量 #9、BM25 #2、融合后 **#2**，top-3 稳稳命中。也要诚实说一句：hit@1 上 RRF 比纯向量还低一名（5 对 6）——融合偏好两路共识的块，个别纯向量状元会被挤到第二。但 k≥3 之后它全面追平并反超，而 RAG 场景本来就要给模型喂 top-3，这个交换划算。

## 五、rerank：文件对了，小节还要对

RRF 把正主文件救回了 top-3，但还有个暗伤：翻车题融合后的第一名是收官篇的「服务器注册表」小节——沾边，但不是答案本体。引用溯源以块为单位，**块不准，给读者的出处就是错的**。

这就是 rerank（重排序）的位置：检索是粗排，求快；rerank 是精排，求准。工业界用 cross-encoder 小模型逐块打分，我们手里现成的是大模型，直接演示——把 top-10 候选编号塞给模型，一次请求打出 0~10 分，只许返回 JSON 数组：

```go
fmt.Fprintf(&b, "问题：%s\n\n下面 %d 个资料块，请评估每块对回答该问题的相关程度，"+
	"打 0~10 的整数分（10=直接给出答案，0=完全无关）。 "+
	"只输出一个 JSON 数组，长度 %d，不要输出任何其他内容。\n\n", question, len(cands), len(cands))
for i, c := range cands {
	text := []rune(c.Chunk.Text)
	if len(text) > 400 { // 块最长 400 字，控制单次请求体量
		text = text[:400]
	}
	fmt.Fprintf(&b, "[%d] %s\n\n", i+1, string(text))
}
```

实测（`go run ./rag/cmd/rerankdemo`，deepseek-v4-pro 打分）前后对比：

| 名次 | 重排前（RRF） | 重排后（LLM 打分） |
| --- | --- | --- |
| 1 | 收官篇 §服务器注册表 | **远程MCP §一个端点，两种方法（10 分）** |
| 2 | 远程MCP §一个端点，两种方法 | 远程MCP §会话与协议版本头（9 分） |
| 3 | 手写篇 §stdio 循环 | 远程MCP §安全三件套（8 分） |

正主小节 10 分登顶，原第一名只拿 4 分掉到第六。成本也要交代：10 块一次打分整段跑了约 42 秒，全耗在这一发 LLM 调用上——生产环境该换 bge-reranker 这类 cross-encoder，毫秒级出分；rerank 只对粗排的 top-10~20 用，别全量。
