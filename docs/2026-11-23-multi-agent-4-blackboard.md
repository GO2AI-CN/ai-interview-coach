# Agent 各干各的互不知情？加一块共享黑板就搞定

前两篇我们先后解决了多 Agent 协作的两个问题：编排者派活（主从编排）、Worker 之间传话（Handoff 交接包）。但 RunChain 有一个绕不开的瓶颈——它是线性的：研究员不交卷，压测员就不能开工；压测员不写完交接包，顾问只能干等。

现实中的调研任务不是流水线，更像一间作战室：压测完全可以先跑主流候选，调研冒出中间结论随时贴上墙，谁有空谁看。这就是本文的主角——黑板模式。

## 线性流水线的天花板

RunChain 的「每一棒只看上一棒交接包」是个好习惯，但它隐含了两个浪费：

1. **串行等待**：三棒耗时是三者之和。调研 5 分钟、压测 8 分钟、出结论 2 分钟，一共 15 分钟——而压测和调研明明可以同时进行；
2. **信息单向**：交接包是点对点的，A 棒的产出 B 棒看不见，除非编排者主动转交。系统里没有一个「谁都能看」的公共记忆。

把协作方式从「接力跑」换成「围一块白板干活」，这两个问题就同时消失了。

这个模式不是我们的发明。二十世纪的专家系统 HEARSAY-II 就用黑板协调多个语音识别专家模块，各自独立打分、随时读取别人的中间结果；今天 LangGraph、AutoGen 这类框架里的共享状态，本质也都是黑板。我们只是用最朴素的 Go 数据结构把它重新实现一遍——理解了原理，用不用框架你都有底气。

## 黑板模式：把公共记忆从 Agent 手里拿出来

黑板模式的想法很朴素：Agent 们共享一块黑板，谁有结论就贴一张便签上去，谁需要信息就到对应分区读，读完也可以回贴新结论。没有任何 Agent 掌握全局，黑板本身就是全局。

它和 Handoff 不是替代关系，而是互补。两者怎么选，看这张对比表：

| 维度 | Handoff 交接包 | 共享黑板 |
| --- | --- | --- |
| 协作拓扑 | 点对点，一条接力链 | 广播式，多对多 |
| 数据可见性 | 只有下一棒可见 | 所有 Agent 可见 |
| 适合场景 | 步骤严格依赖、顺序明确 | 可并行、需要互相围观进度 |
| 上下文纪律 | 强制每棒只看交接包 | 要自己克制，别贴流水账 |
| 状态归属 | 在链路里传递 | 收敛到黑板上，随时可审计 |

一个成熟的 Agent 系统里两者都有：粗粒度阶段之间用 Handoff 交接，阶段内部并行时用黑板共享进度。

## 四十行实现并发安全的黑板

黑板的核心是一个带读写锁的分区便签板。便签只要两个字段——谁写的、写了什么；黑板提供三个操作——贴、读分区、读全板快照：

```go
// Note 是贴在黑板上的一个便签：谁写的、写了什么。
type Note struct {
	Author  string // 写便签的 Agent 名
	Content string // 便签内容，一条结论或一条数据
}

// Blackboard 是 Agent 们共享的一块黑板：
// 谁有结论谁就贴一张便签上去，谁需要信息就来读对应分区。
type Blackboard struct {
	mu    sync.RWMutex
	board map[string][]Note // 分区名 → 该分区的便签列表
}

// Pin 往指定分区贴一张便签，并发安全，多个 Agent 可同时写。
func (b *Blackboard) Pin(section, author, content string) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.board[section] = append(b.board[section], Note{Author: author, Content: content})
}
```

注意 `Section` 返回的是副本而不是切片引用——黑板上的便签可能被别的 Agent 并发追加，把内部切片直接交出去，等于把锁架空了。快照方法则把整块黑板渲染成文本，适合直接喂给负责汇总的 Agent。

## 实测：压测员不等调研交卷就开跑

demo 里研究员和压测员在两个 goroutine 里并发干活。压测员开局第一件事不是等交接包，而是读黑板「调研」分区——读到什么用多少；测完把数据贴进「压测」分区，研究员抬眼就能看到。两人完工后，顾问只读一次黑板快照就出结论。实际运行输出：

```text
压测员开局读到 1 条调研便签
---- 黑板快照 ----
【调研】
- [researcher] 候选：fasthttp / net/http+chi / fiber
- [researcher] fiber 与 fasthttp 同源，二选一即可

【压测】
- [benchmarker] QPS：fasthttp 118k / fiber 112k / chi 96k
```

注意第一行：压测员开局只读到 1 条便签——因为两个 goroutine 在赛跑，研究员第二条便签还没贴上。这不是 bug，恰恰是黑板模式的价值：**读到部分信息就开工，看到新便签再补充**，系统整体 latency 由最长的那一棒决定，而不是各棒之和。

## 踩坑记录：黑板不是垃圾场

黑板给了 Agent 自由读写权，也意味着没人替你约束内容质量。三个血泪经验：

**第一，分区是纪律，不是建议。** 所有便签都贴进一个「默认区」，等于把白噪声广播给所有人。分区名就是领域词汇：「调研」「压测」「结论」，Agent 读板时按分区取数，提示词里写清楚各自负责哪个区。

**第二，便签一条一个结论。** 「我们试了 fasthttp 发现不错但后来觉得 chi 也行」这种话贴上去，下游 Agent 没法用。便签的粒度和 Handoff 的证据条目一致：一条便签 = 一条可引用的结论或数据。

**第三，快照里的每条都要带作者。** 出了问题（比如压测数据明显异常）要能追责到棒，这也是 Evidence 字段在黑板上的延续。

另外一个容易忽略的点：**黑板是有状态的服务，生命周期要和任务对齐。** demo 里黑板随进程生灭没关系，但接上大模型之后，一个调研任务可能跑十几分钟，期间黑板要能扛住高频并发读写；进程重启后，未完成的黑板状态要不要恢复（比如持久化到磁盘），需要在工程上提前决定。本系列第 7 篇讲降级与容错时会回来处理这个问题。

最后提醒一句：黑板模式虽好，别什么协作都上黑板。三步以内的线性任务，RunChain 加 Handoff 就够了，黑板的自由度反而引入协调成本。模式是工具，不是炫技。
