# Agent 卡死怎么办？给每棒装上超时、熔断与降级

前面六篇，我们让多 Agent 系统跑得起来、传得上话、并得了行、看得见质量。但只要上线跑过真实流量的人都知道，还缺最关键的一环：**系统挂了怎么办？**

场景很具体：压测员调的大模型接口突然不返回了，HTTP 连接悬在半空。编排者在 `Run` 里干等，顾问在 `WaitFor` 里干等，整条链路像被点了穴。没有超时，你连「它死了」这个判断都做不出来。本文给每个 Agent 装上四道保险丝：超时、重试、熔断、降级。

## 一个 Worker 卡住，全军覆没

多 Agent 系统的故障传播比单 Agent 快得多。单 Agent 卡死只死一个调用；多 Agent 里，一个 Worker 卡住会产生连锁反应：

1. 编排者的派发循环阻塞，后续所有子任务排队等死；
2. 黑板上等它数据的 Agent 全部超时，各自抛错；
3. 用户侧看，请求没有失败、没有返回，就是无限期挂起——最糟的一种故障形态。

所以保险丝的第一要务不是「恢复」，而是**快速失败**——把「无限期等待」变成「明确报错」，让故障可被处理。四道保险丝各司其职，也各有盲区：

| 保险丝 | 防什么 | 防不住什么 |
| --- | --- | --- |
| 超时 | 单次调用卡死 | 反复超时浪费时间 |
| 重试 | 瞬时抖动 | 持续性故障越试越糟 |
| 熔断 | 持续性故障拖垮链路 | 单点偶发错误 |
| 降级 | 错误直接击穿业务 | 兜底结果质量下降 |

注意最后一列：四道保险丝没有一道是万能的，这正是它们要组合使用的原因。还有一层组合关系藏在时间维度上：超时和重试是「单次调用内」的防线，熔断是「跨调用」的防线，降级是「业务层」的最后一道。三道防线从里到外，任何一道失守都有外层接着，这正是分层防御的思路。

## Guard：一个包装器，四道保险丝

设计上是典型的装饰器模式：Guard 实现 `Agent` 接口，包住一个 Agent，外面看毫无区别——直接 `Register` 进编排者就行。四道保险丝全部通过 Option 配置，缺哪道就不装哪道：

```go
// Run 执行被保护的调用：先试熔断，再按"超时+重试"循环，
// 全部失败则计数并走降级。
func (g *Guard) Run(ctx context.Context, t Task) (Result, error) {
	if err := g.tryAcquire(); err != nil {
		return g.degrade(t, err) // 熔断中：快速失败，不触达下游
	}
	var lastErr error
	for i := 0; i < g.maxAttempts; i++ {
		if i > 0 {
			time.Sleep(200 * time.Millisecond) // 重试间隔；生产可换指数退避
		}
		attemptCtx, cancel := context.WithTimeout(ctx, g.timeout)
		r, err := g.agent.Run(attemptCtx, t)
		cancel()
		if err == nil {
			g.onSuccess()
			return r, nil
		}
		lastErr = err
	}
	g.onFailure()
	return g.degrade(t, lastErr)
}
```

几个值得说的设计点。熔断判定放在**进入前**而不是失败后——冷却期内的新调用直接被拒，连下游都不碰，这是「快速失败」的精髓；降级通过 `fallback` 函数注入，兜底产出由业务方决定，Guard 自己不做任何业务假设。

## 实测：三个场景，三道保险丝各救一次

demo 里的 Worker 全是脚本演员，但表演的都是真实故障。场景 A：第一次调用挂起 5 秒（Guard 给的超时只有 100 毫秒），被 `context` 准时切断，重试后第二次成功。场景 B：Worker 每次都返回 500 错误，连续失败 2 次后熔断器打开，第三次调用被快速拒绝。场景 C：错误无法恢复，降级兜底直接产出参考结论。实际输出：

```text
==== 场景 A：超时 100ms，重试 3 次 ====
结果="第 2 次尝试成功" err=<nil>，实际调用次数=2
==== 场景 B：连续失败 2 次熔断，冷却 500ms ====
第 1 次调用：模型接口 500
第 2 次调用：模型接口 500
第 3 次调用：multi: 熔断中，调用被拒绝（500ms 后重试）
```

场景 B 第三行最关键：从发起调用到收到拒绝，没有任何一次网络请求——熔断器把持续故障的开销从「每次一次真实调用」压到了「一次内存判断」。对一个本来就被打挂的下游来说，这是救命的区别。

另外注意冷却机制的设计：熔断不是永久拉黑，冷却期过后会放行一次「试探调用」——成功就恢复计数，失败就重新熔断。这是经典的半开状态，避免了下游恢复后系统还在拒绝服务的尴尬。demo 为了输出简洁没演示恢复路径，代码里 `tryAcquire` 放行冷却期后的首次调用就是留的这个口子。

## 踩坑记录：保险丝也会烫手

**第一，超时要 Agent 配合才有效。** `context.WithTimeout` 只是给调用标了死线，被调的 Worker 必须 `select ctx.Done()` 才能真正退出。demo 里 flaky worker 故意监听 `ctx.Done()`，否则 goroutine 照样睡到 5 秒自然醒，泄漏在后台。接真实 SDK 时同样要确认：库的 context 支持是「真取消」还是「假参数」。

**第二，熔断的计数是跨调用的。** 连续失败 2 次才熔断，意味着第二次失败的调用本身是被放行的——阈值别设太低，否则单点偶发抖动也会触发熔断，误伤正常流量。demo 用 2 是为了快速演示，生产环境一般从 5 起步配退避重试。

**第三，降级不是吞掉错误，要留痕。** `degrade` 成功兜住错误后，对上游表现为正常返回——如果不上报，轨迹评测（第 6 篇）看到的是一条完美链路，实际却是降级货。正确姿势是降级触发时往黑板贴一条「本棒已降级」的便签，或往轨迹里写一条带标记的 Span。真实业务里，「静默降级」比「明确报错」更害人。

完整代码在仓库的 `multi/guard.go` 和 `cmd/multi-guard-demo/`，`go run ./cmd/multi-guard-demo` 复现三个场景。
