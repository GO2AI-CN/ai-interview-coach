# 大模型为什么总胡说八道？RAG 实战第一讲

> 系列三「RAG 与向量检索」第 1 篇。这个系列我们会做一个真正能跑的 **Go 文档问答助手**：把本仓库 `docs/` 下已发布的 16 篇教程 ingest 进去，你问"面试历史怎么落库"，它从文章里找出相关段落、带着出处回答你。

把公司的 Wiki 文档喂给聊天机器人，新人问一句"咱们项目的重试策略是什么"，AI 答得天花乱坠——三分之一摘自文档，三分之一是别的项目的经验，还有三分之一干脆是它编的，文档里根本没写过。

不是模型不够聪明，是你没给它"查资料"的能力。这个能力就是 RAG（Retrieval-Augmented Generation，检索增强生成），也是当下 AI 应用开发的标配技能。这个系列用 Go 从零做到上线，第一篇先把原理和第一性原理讲透，并且**不写一行外部依赖，手写一个暴力语义搜索**。

## 一、幻觉不是模型调皮，是架构使然

LLM 的"胡说八道"有三个结构性成因，换更强的模型也治不了本：

1. **知识截止**：模型权重里封存的是训练截止日的世界，之后的库版本、新协议、你昨天写的文档，它一概不知。
2. **私域知识为零**：你们团队的接口约定、线上排障记录、内部设计文档，从未出现在任何训练语料里。
3. **必须作答**：模型被训练成"永远给出一个流畅的回答"，而不是"不知道就说不知道"。于是它用通用模式脑补细节——这就是幻觉。

三条里，前两条靠"给它资料"解决，第三条靠"要求它只根据资料回答"解决。RAG 恰好同时做这两件事。

## 二、三条路对比：微调、长上下文、RAG

让模型掌握新知识，业界有三条路线。先收藏这张表，面试也考：

| 方案 | 原理 | 知识时效性 | 成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| 微调 | 继续训练模型权重 | 差，重新训练才能更新 | 高（GPU + 标注数据） | 改语气、学格式、垂直领域推理风格 |
| 超长上下文 | 把文档全文塞进 prompt | 好 | 按 token 计费，文档越多越贵 | 文档总量小（几篇以内）的临时问答 |
| **RAG** | 检索出相关段落再生成 | 好，文档更新即生效 | 低，一次嵌入长期复用 | **私域知识问答的主力方案** |

一句话记住：**微调改的是"能力"，RAG 补的是"知识"**。公司文档问答这种知识天天变的场景，RAG 几乎是唯一正解。

## 三、RAG 三段式：先建索引，再检索，最后生成

RAG 把系统分成离线索引和在线问答两条链路：

- **离线索引（ingest）**：加载文档 → 切成小段（chunk）→ 每段调用 Embedding 模型变成向量 → 存进向量库。
- **在线问答（query）**：用户问题也变成向量 → 在向量库里找最相似的 top-k 段 → 把"问题 + 段落"一起拼进 prompt → LLM 只依据段落作答，并标注出处。

看起来只是"先搜索再提问"，但和关键词搜索有本质区别：用户问"怎么让程序常驻后台"，文档里写的是"使用 systemd 守护进程"——没有一词相同，语义却一致。**向量检索找的是"意思相近"，不是"字面相同"**，这正是第 5~6 篇要花大力气调优的核心战场。

## 四、第一性原理：把文本变成向量，用余弦算距离

Embedding 模型本质是一个函数：输入一段文本，输出一个定长浮点数组（比如 1536 维）。训练好的模型有个美妙性质：**语义相近的文本，向量在空间里的距离也近**。

距离怎么算？最常用余弦相似度——只看两个向量的夹角，不看长度。夹角越小越相似，值域 [-1, 1]。对归一化（长度缩放到 1）后的向量，余弦相似度就是点积，几行 Go 就能写完：

```go
// dot 计算点积。输入均为单位向量时，返回值即余弦相似度：1 最像，0 无关。
func dot(a, b []float64) float64 {
	var s float64
	for i := range a {
		s += a[i] * b[i]
	}
	return s
}
```

检索就是：把每段文档预先算好向量存起来，查询来了算一次向量，然后和库里所有向量各做一次点积，排序取前 k 个。暴力、好懂、且在小数据量下完全够用——数据大了才需要 HNSW 这类近似索引（第 4 篇讲）。

## 五、60 行 Go 手写一个暴力语义搜索

为了让大家对"文本 → 向量"有手感，先不调用任何 API，手工造一个玩具 embedding：统计字符一元组和二元组的出现次数，装进 4096 维向量再归一化。真正的 embedding 是神经网络训出来的，这里先用统计学玩法揭示 mechanics：

```go
// naiveEmbed 把文本变成定长向量：统计字符一元组 + 二元组的出现次数。
// 归一化后，两个向量的点积就等于余弦相似度（cosine 函数里直接用）。
func naiveEmbed(text string, dims int) []float64 {
	vec := make([]float64, dims)
	runes := []rune(strings.ToLower(text))
	for i := 0; i < len(runes); i++ {
		vec[int(runes[i])%dims]++ // 一元组：单个字符的贡献
		if i+1 < len(runes) {
			bigram := int(runes[i])<<16 | int(runes[i+1])
			vec[bigram%dims]++ // 二元组：相邻两个字符一起贡献
		}
	}
	return l2norm(vec)
}
```

搜索主循环就是"算向量 → 点积 → 排序"，没有任何魔法：

```go
qv := naiveEmbed(q, 4096)

type hit struct {
	score float64
	doc   string
}
var hits []hit
for _, d := range docs {
	hits = append(hits, hit{dot(qv, naiveEmbed(d, 4096)), d})
}
sort.Slice(hits, func(i, j int) bool { return hits[i].score > hits[j].score })
```

## 六、玩具的边界，正是真 embedding 的价值

上面的 demo 揭示了向量检索的全部 mechanics：表示、度量、排序。它的天花板也很清楚：**手工统计只能捕捉字面共现，捕捉不了语义**。真实世界里"部署/常驻/守护/开机自启"说的是一回事，字符却完全不同。

打破这个天花板的就是训练好的 Embedding 模型：它在大规模语料上学习过"什么句子和什么句子意思接近"，输出的向量天然把语义相近的文本拉到一起。好消息是这类模型到处都是、还便宜——OpenAI 的 `text-embedding-3-small` 每百万 token 约 $0.02，把 16 篇文章嵌入一遍的成本以分钱计。
