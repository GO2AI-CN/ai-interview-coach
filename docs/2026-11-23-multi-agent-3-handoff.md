# 上下文总断片？给 Agent 设计一个 Handoff 交接包

上一篇我们搭好了主从编排：编排者拆任务、派任务，Worker 各司其职。但 demo 跑起来你会发现一个尴尬的细节——第二棒的输入写的是「见上一步调研产出」。

真实的多 Agent 系统里，这句话就是灾难的开始。三个 Agent 接力干活，传话全靠「见上文」，第二轮之后上下文就开始断片：压测员不知道候选清单有哪些，顾问拿不到压测数据，每一棒都在猜上一棒想说什么。本文给这个问题一个工程化的解法——Handoff 交接包。

## 「接着上文」为什么会翻车

单 Agent 多轮对话里，历史消息天然在场，Agent 随时可以翻回去看。但多 Agent 协作不是对话，是接力：每一棒换了「选手」，它只看到编排者塞给它的输入。

「见上文」式传话有三个致命伤：

1. **上下文不可移植**：另一个 Agent 的提示词、角色设定不同，同一句话它读起来意思全变；
2. **长度失控**：把上一轮完整输出原样塞给下一轮，三轮之后提示词就爆了，还全是噪声；
3. **责任不清**：结论没有出处，下一棒无法验证，错了都不知道错在哪一棒。

解决思路借鉴人类团队的做法：离职交接文档。没人交接时说「工作见邮件记录」，都是写一份结构化文档——我做了什么、还剩什么、依据是什么。Agent 之间同样需要这份文档，我们叫它 Handoff。

## Handoff 三要素：摘要、待办、证据

一个合格的交接包只有三个字段，每个字段对应一个明确的问题：

- **交接摘要（Summary）**：上一棒干了什么？结论先行，一段话讲完；
- **待办清单（Todos）**：下一棒要做什么？动词开头，一条条可执行；
- **证据（Evidence）**：结论凭什么成立？每条结论挂一个出处——文件、URL 或实测输出。

三要素缺一不可：没有摘要，下一棒要通读全文自己提炼；没有待办，下一棒不知道该干嘛；没有证据，整条链路的可信度就没了。反过来，交接包里也不该出现的东西是**过程叙述**——「我先试了 A 再试了 B 发现不行」这种流水账对大模型是噪声，只留结论。

写完一份交接包，可以用下面这张自检清单过一遍：

| 检查项 | 不合格的典型样子 | 合格标准 |
| --- | --- | --- |
| 摘要是否结论先行 | 罗列过程：「我先调研了……」 | 一段话讲清结论与现状 |
| 待办是否可执行 | 「关注一下性能问题」 | 「对 3 个候选跑同条件 QPS 基准」 |
| 证据是否挂出处 | 「官方说性能很好」 | 「零分配设计 ← fasthttp README 基准章节」 |
| 是否去掉了过程流水账 | 大段「尝试了 A 又尝试了 B」 | 只留最终结论 |

## 三十行代码定义交接包

三要素落到 Go 里就是一个结构体，外加一个把交接包渲染成文本块的方法——大模型对结构化文本块的利用率，比散落的自然语言高得多：

```go
// Handoff 是 Worker 之间交接工作的"信封"。
// 设计原则只有一条：拿到 Handoff 的人不需要回头追问上一棒，
// 只看这个结构体就能独立开工。这就是"上下文自给自足"。
type Handoff struct {
	Summary  string            // 交接摘要：结论先行，一段话讲清上一棒干了什么
	Todos    []string          // 待办清单：下一棒需要完成的具体动作
	Evidence map[string]string // 证据：每条结论 → 出处（文件路径、URL、实测输出）
}

// String 把交接包渲染成可直接塞进提示词的文本块。
func (h Handoff) String() string {
	var b strings.Builder
	fmt.Fprintf(&b, "【交接摘要】\n%s\n\n【待办】\n", h.Summary)
	for i, t := range h.Todos {
		fmt.Fprintf(&b, "%d. %s\n", i+1, t)
	}
	if len(h.Evidence) > 0 {
		b.WriteString("\n【证据】\n")
		for claim, src := range h.Evidence {
			fmt.Fprintf(&b, "- %s ← %s\n", claim, src)
		}
	}
	return b.String()
}
```

渲染出来的文本块直接填进下一棒的 `Task.Inputs`，不用做任何 prompt 加工——结构本身就是最强的提示。

## RunChain：每一棒只看交接包

有了交接包，接力流水线的实现就顺理成章了。关键是**限制可见性**：每一棒只能看到总目标和上一棒的交接包，看不到更早的历史。这不是缺陷，是刻意的解耦——它逼着每一棒写出自包含的交接包，也让任意一棒可以被替换、被重跑：

```go
// RunChain 把一串 ChainStep 串成接力跑。
// 每一棒只能看到：总目标 Task + 上一棒的 Handoff，
// 看不到更早的对话历史——这正是我们想要的解耦。
func RunChain(ctx context.Context, t Task, steps []ChainStep) (Result, error) {
	var (
		prev Handoff // 第一棒的输入是空交接包
		last Result
	)
	for i, step := range steps {
		r, next, err := step(ctx, t, prev)
		if err != nil {
			return Result{}, fmt.Errorf("multi: 第 %d 棒交接失败: %w", i+1, err)
		}
		prev, last = next, r
	}
	return last, nil
}
```

拿我们的「技术调研助手」跑一遍：研究员圈定三个 Go Web 库候选，把压测待办和出处写进交接包；压测员**不认识研究员**，只读交接包里的待办照单执行，测完 QPS 和内存分配，再写一份新交接包交给顾问；顾问同样只凭交接包给出选型结论。实际运行的输出：

```text
---- 压测员收到的交接包 ----
【交接摘要】
已圈定 3 个 Go Web 库候选，需要压测数据支撑选型
【待办】
1. 对 3 个候选跑同条件 QPS 基准
2. 记录各自内存分配表现
【证据】
- fasthttp 零分配设计 ← github.com/valyala/fasthttp README 基准章节
```

注意最后一棒的结论很有意思：压测最快的 fasthttp 没被选中，顾问结合「内部 API 网关对极限 QPS 不敏感」这个目标，选了长期维护成本最低的 net/http+chi。这就是接力的价值——每一棒只做一件事，但组合起来的判断比任何一个单 Agent 都全面。

## 踩坑记录：什么该进交接包

跑通之后回头复盘，有两个反直觉的经验值得记住。

**第一，交接包不是越长越好。** 早期版本我把每个 Agent 的中间推理都塞了进去，结果下游 Agent 被无关信息带偏——它会把上一棒的猜测当成事实引用。交接包只放「结论 + 待办 + 证据」，推理过程留在本棒的 Result 里供人查看，不进交接链路。

**第二，待办要写给「不认识你的下一棒」。** 「继续优化一下」这种话对熟人有效，对下一棒毫无意义。写待办的自检标准是：一个只看过交接包、对你做过什么一无所知的 Agent，能不能直接执行？不能就重写。

## 小结与预告

本文解决了多 Agent 接力的传话问题：用「摘要 + 待办 + 证据」三要素的 Handoff 交接包替代「见上文」，再用 RunChain 限制每一棒的可见性，逼着交接包上下文自给自足。整个实现不到 80 行 Go 代码，零第三方依赖。

但 RunChain 有一个隐含假设：流程是线性的。现实中多 Agent 经常需要并发干活、随时围观彼此进度——比如压测和调研同时进行，谁有结论谁写上去。这就需要共享黑板模式了。
