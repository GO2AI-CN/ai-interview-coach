## 一、先立规矩：横评比什么

向量库的评测文一搜一大把，但对 Go 开发者有意义的尺子就六把：

- **部署形态**：随进程打包，还是要多养一个服务、一个集群？
- **索引算法**：精确扫描还是 HNSW 这类近似索引——决定规模天花板；
- **过滤能力**：metadata 等值过滤够不够，还是要 SQL 级的组合条件？
- **Go 生态**：有没有官方 Go 客户端，还是只能走 REST 自己糊；
- **运维成本**：备份、监控、升级谁来扛；
- **许可证**：商用有没有坑。

先说一个横评里最容易被骗的点：**嵌入式和独立服务没有高下，是两种工种**。语料十万块以下、单实例部署，嵌入式库把独立服务按在地上摩擦——零网络往返、零运维；语料上了百万、要多实例共享一份索引，独立服务才值回票价。拿着自家语料规模对号入座，比看跑分有用。

## 二、六款向量库一张表

这张表值得收藏。每款的实现语言、许可证、索引能力，我在发稿当天逐条核对过官方仓库和文档：

按场景给结论：

- **十万块以下、单体应用**：chromem-go 或 sqlite-vec。前者纯 Go 零依赖，后者换来完整 SQL——注意它的 Go 绑定要 CGO，本仓库坚持纯 Go 无 CGO，所以没选它；
- **已有 Postgres，且要向量和业务表 JOIN**：pgvector，事务和备份跟着 PG 白捡，写稿时官方 README 的安装命令已到 v0.8.7；
- **十万到千万级、多并发**：Qdrant 或 Weaviate，HNSW 出场；
- **千万级以上、多租户、流式写入**：Milvus，代价是 K8s 集群起步的运维预算。

## 三、chromem-go 边界实测：压到 5 万块

新工具 `rag/cmd/vsbench` 干两件事：给真实库体检，再把规模压上去看曲线。

真实库体检（357 块、bge-m3 1024 维、gzip 落盘）：打开并加载全库 **84.6ms**，落盘仅 **1.3MB**，拿第 6 篇的 10 道考题各查 5 遍 top-3，平均 **230µs**、最慢 400µs。这就是「库太小，问题不成立」的样子。

规模压测用现切的 23 篇教程共 375 块向量做种子，加微小扰动合成 5 千、2 万、5 万块——扰动很小，合成块仍贴在真实语义流形附近：

```go
// v' = normalize(seed + ε·g)：ε=0.05，让合成块仍像真实语料
for j := range v {
	x := float32(s[j] + eps*rnd.NormFloat64())
	v[j] = x
	norm += float64(x) * float64(x)
}
inv := float32(1 / math.Sqrt(norm))
```

压测过程踩了个值得说的坑：Windows 下单次亚毫秒操作的计时并不可靠，第一版直接 time.Since 单次查询，375 块规模测出一排 0s。改成批量计时——每次查询重复 N 遍取平均，N 随规模反比缩放：

```go
reps := 200_000/len(vecs) + 1 // 375 块 → 534 遍，5 万块 → 5 遍
for _, q := range queries {
	t := time.Now()
	for r := 0; r < reps; r++ {
		_, _ = col.QueryEmbedding(ctx, q, 3, nil, nil)
	}
	cdurs = append(cdurs, time.Since(t)/time.Duration(reps)) // 总时长除以遍数
}
```

修正后的实测成绩单（每档 30 次查询，对照组是第 1 篇那种单线程暴力余弦）：

| 规模 | 建库耗时 | top-3 平均 | top-3 最大 | 暴力平均 | 堆内存增量 |
| --- | --- | --- | --- | --- | --- |
| 375 | <1ms | 0.21ms | 0.29ms | 0.20ms | 2 MB |
| 5,000 | 5.0ms | 2.7ms | 2.9ms | 3.1ms | 21 MB |
| 20,000 | 18.1ms | 11.0ms | 20.7ms | 12.6ms | 82 MB |
| 50,000 | 47.1ms | 25.1ms | 26.6ms | 31.1ms | 204 MB |

三个结论。第一，**内存账目干净**：每块 1024 维 × 4 字节 ≈ 4KB，堆内存随块数严格线性，5 万块 204MB 一分不差。第二，**查询延迟同样线性**：chromem-go 是精确扫描，没有索引可抄近路——它只比手写暴力快一点点（50k 档 25ms 对 31ms），那 20% 是工程细节，不是算法。第三，**边界自己算**：单查询延迟 = 块数 × 0.5µs 左右，再乘上你的并发数，超过接口预算就该换 HNSW 了。对个人知识库，5 万块、25ms 依然够用；对要扛并发的在线服务，这张表就是换乘站的路标。

## 四、Agentic RAG 与 GraphRAG：追不追

收官回避不了两个热词，说实话的时间到了。

**Agentic RAG** 是把检索变成工具调用：模型自己决定查不查、查几次、查哪个集合，查完不满意再换个问法。听着新，其实你早就见过它的骨架——我们 MCP 系列第 5 篇的函数调用循环，把工具从「查 SQLite」换成「搜向量库」，就是 Agentic RAG。它适合答案散落在多处、需要多步拼凑的问题；代价是延迟和 token 翻倍涨。

**GraphRAG** 先抽实体和关系建图，再沿图检索，治「A 和 B 是什么关系」这类多跳问题。它适合实体密集的语料；我们 375 块教程文，问题基本是「怎么干」型，用不上。

两条共用同一条军规：**先在评测集里加 10 道对应题型，翻车了再上架构**。第 6 篇的 10 道题就是我们的先例——没有卷子的优化都是玄学，没有翻车型的升级都是追风口。
